## 구현 방향 제안

Java 21, Spring Boot, Gradle Wrapper, PostgreSQL, Flyway로 단일 백엔드를 시작한다. 모듈은 `catalog`, `trade`, `identity`, `upload`, `chat`, `payment`로 나눈다. 공통 HTTP 오류와 환경 설정은 공통 계층에서 관리하고, 거래 상태 전이와 권한 검증은 거래 모듈에서 담당한다. 첫 PR에서 프레임워크와 DB 버전, 실행 명령, 환경 변수 예시를 고정한다.

첫 목표는 **FE가 Mock 제품 목록·상세를 실제 HTTP 요청으로 바꾸는 것**이다. PostgreSQL에 개발용 사용자 두 명, 동네, 카테고리, 대여 제품과 미개봉 판매 제품을 넣어 확인한다. 실제 인증 공급자가 붙기 전에는 로컬·테스트 프로필에서만 테스트 사용자를 사용할 수 있게 한다.

## FE와 먼저 맞출 계약

| 화면과 현재 동작 | 변경 제안 |
| --- | --- |
| 01–03 예산 필터 | 초기 제안은 예산을 원 단위 상한으로 받고, 대여는 `보증금 + 일 사용료 × 사용 일수`, 판매는 판매가를 비교한다. Front가 보여 주는 100만 원 끝값과 상한 없는 조회를 어떻게 연결할지 합의한다. 제품 목록에는 기본 사용 일수를 함께 보내고, 요청 시 서버 견적을 다시 계산한다. |
| 04–06 및 T3–T5 역할과 상태 | 빌리는 사람과 주인이 동일한 `tradeId`를 사용한다. Front가 임시로 화면을 이동하는 곳은 서버의 `status` 및 `currentUserRole`에 연결한다. 06의 보류 해제 문구는 거래 완료와 별도로 결제 상태를 확인한 뒤 표시한다. |
| T4–T7 사진과 제품 등록 | 파일 선택은 FE 미리보기다. 실제 등록에는 `POST /uploads` 응답의 `photoId`를 전달한다. 업로더, 거래 ID, 사진 용도를 검증한다. 프론트 등록 폼에 계약상 필요한 카테고리, 설명, 품목 확인 정보 중 빠진 항목을 맞춘다. |
| M2·C1 역할별 필터 | `GET /trades`와 `GET /chats`에 `role=OWNER|REQUESTER` 필터를 추가하는 안을 제안한다. 서버가 필터를 적용한 뒤 커서를 계산한다. M2에는 제품명과 썸네일 등 카드 표시용 요약이 필요하다. |
| M3 선택과 첫 경험 기록 | 타일 선택과 체크는 화면 상태로 둔다. 첫 경험 집계는 완료 거래의 카테고리에서 계산하고, 반복 이용으로 한 카테고리가 중복 집계되지 않게 한다. |
| C2 반납 날짜와 알림 | 현재 날짜 입력은 채팅 메시지 예시로 처리된다. 실제 반납 기한은 서버가 거래 정책으로 계산한다. 알림 벨은 현재 빈 상태를 표시하므로 알림의 저장·읽음 API는 사용자 시나리오를 정한 뒤 범위를 추가한다. |
| O4–O8 로그인·동네·결제수단 | 공급자 선정 전에는 개발용 사용자와 예시 동네로 화면 이동을 검증한다. 약관 문서 ID·버전, 인증 상태의 응답 형태, 결제수단 표시용 필드를 먼저 합의한다. |

## 데이터와 거래 일관성

- **기반 데이터**는 사용자, 동네와 인증 기록, 정책 버전과 사용자 동의, 카테고리, 제품과 제품 사진이다. 제품은 트랙과 공개 상태를 저장하고, 트랙별 가격 필드를 서버에서 검증한다.
- **거래 데이터**는 견적, 거래, 상태 변경 기록, 거래 사진, 결제 상태·이벤트, 분쟁, 후기다. 견적에 가격과 만료 시각을 저장한다. 같은 상품을 동시에 요청할 때 허용할 주문 수와 재고 기준을 정하고, 결정한 제약을 DB 트랜잭션에서 적용한다.
- **대여**는 `REQUESTED → ACCEPTED → READY_FOR_PICKUP → IN_USE → RETURN_SUBMITTED → COMPLETED`를 기본 흐름으로 쓴다. **미개봉 판매**는 `REQUESTED → ACCEPTED → READY_FOR_PICKUP → COMPLETED`를 제안한다. 취소·분쟁의 허용 역할과 상태는 별도로 표로 확정한다.
- 기한은 서버 시각으로 계산하고 API는 시간대를 포함한 ISO 8601을 반환한다. 문고리 주소는 수락 이후 허용 상태의 참여자만 조회한다. 거래 사진도 용도와 참여 권한에 따라 접근을 제한한다.
- 결제와 거래의 상태를 분리한다. 요청 생성은 멱등성 키로, PG 통지는 공급자 이벤트 ID로 중복 반영을 방지한다. DB 기록과 공급자 호출 사이에 중단이 생기면 재시도 때 결제 상태를 조회해 결과를 복구할 수 있게 한다.
- **채팅 데이터**는 거래별 채팅방, 메시지, 사용자별 읽음 위치다. 같은 사용자·채팅방의 `clientMessageId`를 기준으로 재전송을 처리한다. 첫 연결은 HTTP 조회로 검증하고 실시간 전송 필요 여부는 이후 결정한다.

## 리뷰와 검증

1. 단계별로 Back 기능 브랜치와 PR을 만든다. API가 달라지면 Back 계약 문서와 응답 예시를 갱신하고, 연결된 Front PR과 확인 방법을 함께 적는다.
2. 서버 테스트에서 예산 경계값, 오류 JSON, 목록 커서, 두 사용자 역할, 주소와 사진 접근, 재시도와 동시 상태 변경을 검증한다.
3. FE와 연결할 때 정상·빈 상태·실패 응답을 확인하고 기존 스켈레톤, 요청 로딩 모달, 오류 토스트에 연결한다.
